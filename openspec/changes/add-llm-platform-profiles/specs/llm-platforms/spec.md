# Spec Delta

## Purpose

Defines which LLM coding platforms a viber scaffold can target, how the platform is chosen, and how the scaffold and the surrounding `viber init` output adapt to it.

## ADDED Requirements

### Requirement: Supported platforms are selectable at init

`viber init` SHALL accept `--platform <id>` where `<id>` is one of `claude`, `codex`, `gemini`, or `opencode`. When the flag is absent in non-interactive mode the platform SHALL be `claude`. When the interactive wizard runs and the flag is absent, the wizard SHALL ask for the platform, offering the supported platforms with `claude` preselected. An `<id>` that is not supported SHALL be a usage error (exit `2`) whose message lists the supported ids, and it SHALL be detected before anything is written to disk.

#### Scenario: Explicit platform

- **WHEN** the user runs `viber init myproj --platform codex`
- **THEN** the scaffold is generated for the `codex` platform

#### Scenario: Default platform

- **WHEN** the user runs `viber init myproj` without a terminal on standard input
- **THEN** the scaffold is generated for the `claude` platform

#### Scenario: Wizard asks for the platform

- **WHEN** the user runs `viber init` on a terminal with no arguments and no `--platform`
- **THEN** the wizard prompts for the platform with `claude` preselected, and the chosen value is used

#### Scenario: Unknown platform

- **WHEN** the user runs `viber init myproj --platform cursor`
- **THEN** the command exits `2`, prints an error naming `cursor` and listing `claude`, `codex`, `gemini`, `opencode`, and creates no directory

### Requirement: Every scaffold carries the platform-neutral core

Whatever the platform, a scaffold SHALL contain `AGENTS.md`, `intend.md`, `README.md`, `Makefile`, `.gitignore`, `.markdownlint.yaml`, the `scripts/` helpers, and the rules documents (git hygiene, testing, security, error handling, documentation, output style, release notes, pre-commit checklist). `AGENTS.md` SHALL state the project name and description and SHALL point to `intend.md`.

#### Scenario: Core present for each platform

- **WHEN** a scaffold is generated for each of `claude`, `codex`, `gemini`, and `opencode`
- **THEN** each contains `AGENTS.md`, `intend.md`, `README.md`, `Makefile`, `.gitignore`, `.markdownlint.yaml`, and `scripts/sync-issues.sh`

### Requirement: Claude scaffold keeps the full Claude Code integration

For the `claude` platform the scaffold SHALL contain `CLAUDE.md` importing `AGENTS.md`, the sub-agent team under `.claude/agents/`, the project commands under `.claude/commands/`, the rules under `.claude/rules/`, `.claude/settings.json` with its hooks, and `docs/team.md`. The file tree and content of a scaffold generated without `--platform` SHALL be identical to the one generated before platforms existed.

#### Scenario: Default scaffold is unchanged

- **WHEN** a scaffold is generated for `claude` with the same name and description as a scaffold generated by the previous release
- **THEN** both file trees have the same paths and the same file contents

### Requirement: Non-Claude scaffolds contain no Claude Code artifacts

A scaffold for `codex`, `gemini`, or `opencode` SHALL NOT contain `CLAUDE.md`, a `.claude/` directory, or `docs/team.md`, and none of its files SHALL mention Claude Code, `.claude/`, `/plugin`, or `/opsx:`-style Claude slash commands.

#### Scenario: Codex scaffold is Claude-free

- **WHEN** a scaffold is generated for `codex`
- **THEN** no path in it is `CLAUDE.md`, starts with `.claude/`, or is `docs/team.md`, and no file contains the text `Claude Code`

### Requirement: Platforms that need their own entry file get one

For `gemini` the scaffold SHALL contain `GEMINI.md` that imports `AGENTS.md` on a line of its own and does not repeat the project description. For `codex` and `opencode`, which read `AGENTS.md` natively, no extra entry file SHALL be generated.

#### Scenario: Gemini entry file

- **WHEN** a scaffold is generated for `gemini`
- **THEN** `GEMINI.md` exists and contains a line that is exactly `@AGENTS.md`

#### Scenario: Native AGENTS.md readers

- **WHEN** a scaffold is generated for `codex` or `opencode`
- **THEN** the only top-level instruction file is `AGENTS.md`

### Requirement: Rules stay reachable on platforms that do not auto-load them

For platforms whose tool does not load rule files from a conventional directory, the rules documents SHALL be placed in `docs/rules/` and `AGENTS.md` SHALL list them with a one-line instruction to follow them. For `claude`, where the tool loads `.claude/rules/` itself, `AGENTS.md` SHALL NOT mention `.claude/`.

#### Scenario: Rules listed for codex

- **WHEN** a scaffold is generated for `codex`
- **THEN** `docs/rules/` holds the rules documents and `AGENTS.md` names each of them

#### Scenario: No `.claude/` in AGENTS.md for claude

- **WHEN** a scaffold is generated for `claude`
- **THEN** `AGENTS.md` does not contain `.claude/`

### Requirement: Platform-specific wording follows the platform

Prose in the scaffold that names the coding tool, the command that starts it, or the OpenSpec explore command SHALL use the selected platform's values: `README.md` prerequisites and quick start, `intend.md` guidance, and the `viber init` next-steps output.

#### Scenario: README for gemini

- **WHEN** a scaffold is generated for `gemini`
- **THEN** `README.md` links the Gemini CLI as the prerequisite, tells the user to run `gemini`, and does not mention `claude`

#### Scenario: Next steps for the chosen platform

- **WHEN** `viber init myproj --platform codex` succeeds
- **THEN** the printed next steps include `codex` as the command to start and the platform's OpenSpec explore command, and do not include `claude`

### Requirement: OpenSpec is initialised for the selected platform

After rendering, `viber init` SHALL initialise OpenSpec non-interactively for exactly the selected platform's OpenSpec tool, so the generated OpenSpec skills and commands match the scaffold. A failure of that step SHALL be a runtime error (exit `1`) naming the operation.

#### Scenario: Tool derived from platform

- **WHEN** `viber init myproj --platform opencode` runs
- **THEN** OpenSpec is initialised with the `opencode` tool and no interactive tool prompt appears

### Requirement: Platform-specific automation degrades to manual commands

Automation that depends on Claude Code hooks (the issue sync that runs when a `tasks.md` is written) SHALL be shipped only for `claude`. For other platforms the scaffold SHALL still ship `scripts/sync-issues.sh` and the matching `make` target, and `README.md` SHALL state that issue sync is run manually.

#### Scenario: Manual issue sync

- **WHEN** a scaffold is generated for `codex`
- **THEN** `scripts/sync-issues.sh` exists, `README.md` says issue sync is manual, and no hook configuration file exists
